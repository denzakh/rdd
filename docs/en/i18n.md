# i18n strategy (docs/en/i18n.md)

**Status:** spec + partial implementation · **Layer (FSD):** `src/shared/lib/intl` (dictionaries,
locale helpers), `RegistryField.label` / `RegistryOption.label` in `src/shared/config/registry`

## 1. Context & constraints

A clinical registry with ~50+ fields ships Russian-first: clinicians enter data in Russian,
while reviewers/hiring managers read English. Full i18n frameworks (next-intl) would add
routing, message extraction and ICU plural machinery for exactly two locales with no RTL
and no plural-sensitive clinical strings.

Project principle (consistent with auth instead of Auth.js, PBKDF2 instead of bcrypt,
own SQL diff-engine instead of Prisma): **own small solution beats a standard one**
when the standard one costs more than the problem. i18n follows the same pattern —
and is itself a talking point ("why not next-intl").

## 2. Options considered

| Option                                                                                                                                                                                  | Decision                                                                                                                                  |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Plain TS dictionaries per namespace (`dictionaries/{en,ru}.ts`) + React `useT()` hook, locale from cookie (demo: `rdd_locale`; prod candidate: `users.locale` like `data_scope`)** | **ACCEPTED** — cheap, explainable, zero magic, same pattern as row-level access                                                           |
| B. next-intl (standard ecosystem tool)                                                                                                                                                  | Rejected as default: contradicts minimal-dependency principle; portfolio-valid but needs explicit justification — kept as escalation path |
| C. Full CMS-driven translations                                                                                                                                                         | Rejected: no translators in the loop, clinical risk without expert review                                                                 |

## 3. What is translated

- **Static UI strings** (buttons, menus, errors, admin panel, auth forms) — small set,
  mechanical translation + review. Namespaces: `common`, `auth`, `patients`, `reports`,
  `matrix`, `admin`.
- **`field.label.en` in the registry — the field already exists**
  (`{ ru, en } | string`); ~50+ phase/scale labels filled in this change
  (status/therapy/scales), patient/remission/phase already had `en`.
  Resolved via `fieldLabel(field, locale)` with RU fallback.
- **`RegistryOption.label` widened to `{ ru, en } | string`** (was `string`-only):
  DB stores codes (`value`), never text — translating options never rewrites history.
  Resolved via `optionLabel(opt, locale)` with RU fallback.
- **`Intl`-based computations (`calculations.ts`) already locale-aware by construction:**
  `formatDate(date, locale)` takes `locale` (`ru-RU` default) instead of a hardcode;
  pure arithmetic (`diffYears/diffMonths/getAgeGroup`) is locale-independent.

## 4. Locale plumbing (demo quality, explicit)

- Cookie `rdd_locale` (`ru` default, `en` optional), read server-side via
  `getLocale()` (`next/headers`), switched by Server Action `setLocaleAction`
  and the client `<LocaleSwitcher />` in `UserMenu` (no extra dependency).
- No localized routing (`/en/...`): out of scope — one cookie, two dictionaries.
- `formatDate` receives the resolved locale at call sites; no global `Intl` singleton.

## 5. Deliberately OUT of scope (not forgotten)

Following the project's "Demo boundaries" style, explicitly not doing:

- **Translating historical DB values** — not needed: DB holds codes (`options`), not text.
- **Fully localized clinical scales with clinician-native validation** — out of demo scope,
  stated honestly (same as "Medical validation" in architecture-overview).
- **RTL, plural rules (ICU)** — irrelevant for ru/en pair, explicitly not doing.
- **`users.locale` persistence + localized email/audit strings** — candidate for later;
  audit/validation messages stay codes + RU text, not user-facing prose.

## 6. Escalation threshold to next-intl / translation CMS

Revisit (migrate to next-intl or a CMS) if ANY of:

- a third locale appears (esp. RTL) or plural-sensitive clinical strings emerge;
- non-developers (translators) must edit strings without touching code;
- localized routing/SEO (`/en/...`) becomes a requirement.

Until then plain dictionaries are correct: zero magic, typed keys, unit-tested fallback.
