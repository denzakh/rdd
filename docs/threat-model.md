# Threat Model (STRIDE)

**Назначение:** формализация неявной threat model, которая уже зафиксирована в
[architecture-overview.md — Security-сводка](./architecture-overview.md) в формате
«угроза → мера → где реализовано». Здесь те же меры переупакованы по категориям
STRIDE; колонка «Сводка» ссылается на строку первоисточника, где указано, _где
именно_ мера реализована в коде.

> **Метод.** Шесть категорий STRIDE применены к каждой связи контекстной диаграммы
> ([c4-overview.svg](./diagrams/c4-overview.svg)): пользователь → RDD (Next.js на
> Cloudflare Workers) → D1. Для демо-версии часть рисков сознательно принята
> (см. «Не покрыто»); всё, что принято, задокументировано, а не «забыто».

---

## 1. Границы доверия

| Граница           | Что пересекает             | Допущение                                                                          |
| ----------------- | -------------------------- | ---------------------------------------------------------------------------------- |
| Браузер → Workers | HTTPS, сессионная cookie   | Клиент недоверенный: время, значения полей и идентификаторы из запроса не доверяем |
| Workers → D1      | Платформенный binding      | D1 недоступна напрямую извне; инъекция — только через параметры приложения         |
| Admin CLI → БД    | Локальный доступ оператора | Вне сетевой границы; учётки создаёт только admin                                   |

Публичной регистрации нет — модель угроз исходит из «внутреннего злоумышленника»
(существующий пользователь) и «внешнего без аккаунта» (перебор, перехват).

## 2. STRIDE-анализ

### S — Spoofing (подмена идентичности)

| Угроза                                     | Мера                                                                          | Сводка               |
| ------------------------------------------ | ----------------------------------------------------------------------------- | -------------------- |
| Подбор пароля (brute force)                | Rate-limit: 5 неверных паролей → блокировка 15 мин                            | spec-stage-3, README |
| Перебор логинов (enumeration)              | Одинаковая задержка 400 мс для существующих/несуществующих email              | auth.md §6           |
| Перехват сессии через cookie               | `Secure; HttpOnly; SameSite=Lax`, TTL 12 ч, sliding renewal                   | auth.md §5           |
| Слабый хэш пароля (угон БД → оффлайн-крак) | PBKDF2-SHA256, 200k итераций, constant-time сравнение                         | auth.md §4           |
| Выдача себя за пользователя через инвайт   | Регистрация запрещена; учётки только от admin; одноразовые ссылки, TTL 7 дней | auth.md §1–2, §9     |

### T — Tampering (подмена данных)

| Угроза                                  | Мера                                                                                               | Сводка              |
| --------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------- |
| Мутация мимо UI (readonly-роль)         | Двойная проверка: UI `isReadOnly` + `canWrite()` в каждом Server Action                            | spec-stage-1 §1, §3 |
| Инъекция/подмена полей клиентом         | Whitelist `DATA_COLUMNS`, Zod `phaseSchema.partial()`, системные поля не принимаются от клиента    | spec-stage-1 §2     |
| Параллельная запись поверх чужих правок | CAS по `updated_at` из SQLite (клиентским часам не доверяем) + трёхуровневое разрешение конфликтов | matrix.md §6.4      |

### R — Repudiation (отказ от действий)

| Угроза                   | Мера                                                                                                                   | Сводка                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| «Это не я менял данные»  | `actor_id` из `requireUser()` в каждой мутации; аудит (`audit_log`, append-only) атомарно с записью в одном `db.batch` | auth.md §11, matrix.md §6.6 |
| Подмена/затирание аудита | `audit_log` append-only: UPDATE/DELETE запрещены логикой; фиксация overwritten-версий при конфликтах                   | matrix.md §6.6              |

### I — Information Disclosure (утечка информации)

| Угроза                                                                       | Мера                                                                                         | Сводка                                                                                  |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| IDOR: clinician видит чужих пациентов                                        | `data_scope` на пользователе; scope-репозиторий фильтрует `list/listPage/count/findById`     | auth.md — Row-level access                                                              |
| Деанонимизация через агрегаты `/reports` (differencing attack: малые ячейки) | Scope-фильтр во ВСЕХ агрегатах + подавление ячеек < `K_ANONYMITY_K` (5)                      | export.md §3; `queries.ts` (countByField/phaseDurationsByOrder/efficacyByMainComponent) |
| Утечка PII через логи                                                        | В `audit_log` только id и JSON-значения, персональные данные не дублируются                  | matrix.md §6.6                                                                          |
| Утечка БД → угон сессий                                                      | В БД только SHA-256(токен); сырой токен живёт только в HttpOnly cookie                       | auth.md §5                                                                              |
| Чтение чужих ячеек в матрице                                                 | Коллаборация — polling авторизованных; конфликт-дифф видят только участники пациента (scope) | matrix.md §6.4–6.5                                                                      |

### D — Denial of Service (отказ в обслуживании)

| Угроза                        | Мера / принятый риск                                                                                                            | Сводка             |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| Подбор паролей как вектор DoS | Rate-limit на login (см. S)                                                                                                     | spec-stage-3       |
| Флуд Server Actions           | **Принято в демо:** rate-limit на вход — 5→15 мин (этап 3); остальные actions не лимитируются; порог эскалации — Cloudflare WAF | auth.md §12        |
| Перегрузка D1                 | Пейджинг, виртуализация, батчинг мутаций (дебаунс 300 мс)                                                                       | matrix.md §2, §6.1 |

### E — Elevation of Privilege (повышение привилегий)

| Угроза                                    | Мера                                                                            | Сводка                     |
| ----------------------------------------- | ------------------------------------------------------------------------------- | -------------------------- |
| Самостоятельное получение роли            | Регистрация запрещена; роли назначает только admin; `user:create` — CLI, не веб | auth.md §1                 |
| Клиент подменяет свои поля пользователя   | Системные поля (`data_scope`, роль) не принимаются от клиента — whitelist полей | spec-stage-1 §2            |
| Обход scope через прямые запросы к action | Проверка scope на сервере в репозитории, а не в UI                              | auth.md — Row-level access |

## 3. Не покрыто (осознанные риски демо)

Полный список — «Границы демо-проекта» в [architecture-overview.md](./architecture-overview.md).
Наиболее значимые с точки зрения threat model:

- **Rate-limit / WAF на публичные actions** — эскалация на Cloudflare WAF вне кода
  (auth.md §12); критично перед любым публичным доступом.
- **Шифрование at rest, key management, изоляция окружений** — вне scope; D1
  шифруется средствами платформы.
- **Retention / право на забвение** — append-only `audit_log` несовместим с удалением
  PII без отдельного решения (криптографическое стирание или анонимизация).
- **Uptime/алертинг** — отсутствует (см. [nfr.md](./nfr.md), раздел «Мониторинг»);
  инциденты сейчас не детектируются автоматически.
- **Обязательность полей на сервере** — required-логика компенсируется UI; при
  переводе в прод закрыть на уровне Zod-схемы.

> До этапа правок `/reports`-агрегаты были не фильтрованы по scope и не защищены
> выборочным подавлением малых ячеек (k-anonymity) — это позволяло пользователю с
> `data_scope: site` видеть агрегат по всем центрам, а малые группы (count=1..2)
> деанонимизировались через differencing attack. Риск закрыт: агрегаты теперь
> уважают `data_scope` и подавляют ячейки < `K_ANONYMITY_K` (см. строку в §2, I).

**Вывод:** модель строилась вокруг двух осей — _клиент недоверенный_ (все проверки
дублируются на сервере: `canWrite()`, whitelist, scope-репозиторий, CAS) и
_действие всегда прослеживается_ (`actor_id` + append-only аудит атомарно с мутацией).
Отдельные строки таблицы выше — переупаковка уже реализованных мер, новые
обязательства этим документом не вводятся.
