# Развёртывание и эксплуатация: Cloudflare Workers + D1 + CI (./deployment.md)

**Статус:** операционный документ (не спека) — описывает, как система разворачивается и живёт
**сейчас**: целевые ресурсы Cloudflare, ручной деплой, GitHub Actions, работа с прод-базой,
откат и диагностика.
**Опирается на:** `wrangler.jsonc`, `package.json` (скрипты), `scripts/*`, `.github/workflows/ci.yml`,
[nfr.md](./nfr.md) (RTO/RPO), [schema-evolution.md](./schema-evolution.md) (эволюция схемы).

> **Для кого написан.** Документ намеренно «разжёвывает»: предполагается, что читатель раньше
> не деплоил Next.js на Cloudflare и не работал с D1. Каждая команда приводится целиком,
> с ожидаемым результатом и объяснением «зачем». Если нужна только шпаргалка — §0 и §11.

## 0. TL;DR — шпаргалка

```bash
# Первый деплой (делается один раз)
npx wrangler login                 # браузер, вход в аккаунт Cloudflare
npm ci                             # установка зависимостей ровно по lockfile
npm run deploy                     # сборка + загрузка; Cloudflare создаст домен rdd.ux42.studio
npm run db:migrate:remote          # создать схему в облачной D1 (миграции 0001–0007)
npm run user:create:remote         # первый пользователь автоматически станет admin
npm run seed:demo:remote           # (опционально) демо-пациенты

# Обычное обновление кода
git push                           # GitHub Actions прогонит проверки
npm run deploy                     # прод обновится атомарно, данные не тронутся

# Прод-БД с нуля + демо-данные
npm run db:restart:remote:seed     # дамп → DROP таблиц → миграции → демо-данные

# Откат кода на предыдущую версию
npx wrangler rollback
```

> **Windows:** перед `npm run deploy` остановите `npm run dev` (иначе `EPERM`) и убедитесь, что
> `npx wrangler --version` ≥ 4.141 (на старых версиях деплой падает с `…resvg.wasm?module`).
> Подробности и команды — в §9.

Шаг 4 — это именно `npm ci`, а не `npm i`: `ci` ставит зависимости строго по `package-lock.json`
и предварительно удаляет `node_modules`, поэтому на прод уедет ровно то, что проверено в CI.
`npm i` может попутно поправить lockfile и разъехаться с ним. Если `npm ci` падает — см. §9
(чаще всего мешает запущенный dev-сервер или повреждённый `node_modules`).

Где что живёт:

| Сущность                       | Где физически                      | Кто/что создаёт                         |
| ------------------------------ | ---------------------------------- | --------------------------------------- |
| Код воркера `rdd`              | Cloudflare, аккаунт владельца зоны | `npm run deploy`                        |
| Статика (`_next/static` и пр.) | Cloudflare, assets того же воркера | `npm run deploy`                        |
| База данных                    | Cloudflare D1 `rdd` (`5a15f362-…`) | создана один раз (`wrangler d1 create`) |
| Домен `rdd.ux42.studio`        | Cloudflare, Custom Domain воркера  | `npm run deploy` (по `wrangler.jsonc`)  |
| Схема БД                       | репозиторий, `migrations/*.sql`    | `npm run gen:d1` + ручные файлы         |
| Проверки кода                  | GitHub Actions                     | push в `main` или Pull Request          |

Диаграмма соответствия «что в репозитории → что в Cloudflare» — в
[architecture-overview.md](./architecture-overview.md) (C4: L2 Container).

## 1. Что именно мы разворачиваем (модель простыми словами)

**Обычная веб-аппка** едет на сервер (VPS/контейнер): там крутится Node-процесс, перед ним nginx,
рядом база, а деплой = скопировать файлы и перезапустить процесс (отсюда «окна простоя»).

**Здесь всё иначе.** Приложение — Next.js, но в проде это **не Node-процесс**, а один **Worker**:
изолированная JS-программа, которую Cloudflare исполняет на своих edge-узлах. Отдельного сервера
нет — нечего перезапускать, нечего настраивать в nginx, нет «порта 3000».

Как Next.js превращается в Worker:

1. `opennextjs-cloudflare build` (внутри `npm run deploy`) компилирует приложение в
   `.open-next/worker.js` (точка входа, в конфиге это `"main"`) и `.open-next/assets/**` (статика).
2. `opennextjs-cloudflare deploy` вызывает `wrangler deploy`, который загружает результат в аккаунт
   Cloudflare как воркер с именем **`rdd`**.

**База данных — D1** (облачная SQLite). Ключевой момент: воркер **не подключается к БД по строке
соединения с логином и паролем**. Вместо этого в конфиге объявляется **binding** — «провод» от кода
к ресурсу (`DB → база rdd`), и в коде это выглядит как `env.DB`. Хоста, порта и пароля как понятий
не существует, поэтому приложению не нужны секреты (см. §10).

**Статика** уезжает тем же воркером: каталог `.open-next/assets` объявлен как assets-биндинг
`ASSETS`, Cloudflare отдаёт файлы сам, не поднимая приложение.

Итого у приложения три адреса:

| Адрес                               | Что это                          | Когда используется                             |
| ----------------------------------- | -------------------------------- | ---------------------------------------------- |
| `http://localhost:3000`             | `npm run dev` — обычный Next dev | Разработка                                     |
| `https://rdd.<account>.workers.dev` | служебный адрес воркера          | Появляется сам при деплое; удобен для проверок |
| `https://rdd.ux42.studio`           | Custom Domain (свой домен)       | Прод-адрес для клиник и демонстрации           |

**Деплой** = загрузка новой версии кода. Cloudflare создаёт новую версию воркера и **атомарно**
переключает на неё трафик: состояния «половина старой, половина новой» не бывает. База при деплое
**не меняется** — ни строки, ни схемы.

## 2. Карта файлов, влияющих на деплой

| Файл                                  | Роль                                                                                                                | Что будет, если ошибиться                                                         |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `wrangler.jsonc`                      | «Паспорт» воркера: имя, точка входа, биндинги, домен                                                                | Создастся не тот ресурс/домен, потеряется связь с БД                              |
| `open-next.config.ts`                 | Настройки OpenNext (сейчас по умолчанию; в комментариях — вариант с кэшем на R2)                                    | Неверный кэш ISR → устаревшие страницы                                            |
| `next.config.ts`                      | Настройки Next + `initOpenNextCloudflareForDev()` (bindings в `next dev`)                                           | В `npm run dev` не будет `env.DB`                                                 |
| `package.json` → `scripts`            | Что именно запускают команды `npm run …`                                                                            | Запуск «не того» шага (`wrangler deploy` вместо `npm run deploy`)                 |
| `.github/workflows/ci.yml`            | Проверки на push/PR                                                                                                 | Красный CI или, хуже, «зелёный по ошибке»                                         |
| `migrations/*.sql`                    | Схема прод-БД: `0001` — генерируемый baseline, `0002–0007` — ручные                                                 | Прод без новых таблиц/колонок                                                     |
| `scripts/gen-d1.ts`                   | Генератор миграций из TS-реестра полей                                                                              | Рассинхрон реестра и схемы БД                                                     |
| `scripts/db-restart.ts`               | Полный ресет **локальной** БД (baseline + ручные миграции)                                                          | Потеря локальных данных (для dev-базы это нормально)                              |
| `scripts/db-restart-remote.ts`        | Полный ресет **продовой** D1 (+ опционально сеялка)                                                                 | Потеря прод-данных (страховка — дамп, см. §5.6)                                   |
| `scripts/ensure-local-db.ts`          | Накатывает миграции перед интеграционными тестами, если их не хватает                                               | Тесты упадут на «no such table»                                                   |
| `scripts/seed-demo.ts`                | Демо-данные (локально и в прод)                                                                                     | Демо-цифры исказят отчёты на реальных данных                                      |
| `scripts/create-user.ts`              | Создание пользователей (первый получает роль admin)                                                                 | Нет доступа к прод-базе после сброса                                              |
| `image-loader.ts`                     | Свой загрузчик для `next/image` (использует `/cdn-cgi/image/…`)                                                     | Изображения не отдаются — см. §9, пункт про Image Resizing                        |
| `scripts/patch-opennext-turbopack.ts` | Патчит `node_modules/@opennextjs/cloudflare` под Windows (обратные слеши в traced-путях); вешается на `postinstall` | Без него Turbopack-сборка «успешна», но на проде 500 на всех страницах (§5.2, §9) |
| `.open-next/`                         | Артефакт сборки (в git **не** хранится)                                                                             | Прямой `wrangler deploy` задеплоит старую сборку                                  |

## 3. Разбор `wrangler.jsonc` — что там написано и почему

```jsonc
{
  "name": "rdd", // (1) имя воркера в Cloudflare
  "main": ".open-next/worker.js", // (2) точка входа — файл, который создаёт сборка
  "compatibility_date": "2026-03-01", // (3) «диалект» рантайма
  "compatibility_flags": ["nodejs_compat"], // (4) включить Node-совместимые API
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "rdd",
      "database_id": "5a15f362-…",
      "migrations_dir": "migrations",
    },
  ], // (5)
  "routes": [{ "pattern": "rdd.ux42.studio", "custom_domain": true }], // (6)
  "assets": { "binding": "ASSETS", "directory": ".open-next/assets" }, // (7)
  "services": [{ "binding": "WORKER_SELF_REFERENCE", "service": "rdd" }], // (8)
  "observability": { "enabled": true }, // (9)
}
```

1. **`name`** — как воркер называется в Cloudflare. Оно же используется в пункте (8) как имя
   сервиса: **эти два значения обязаны совпадать**. Переименуешь воркер — создастся _второй_
   воркер, а self-reference будет смотреть в старое имя.
2. **`main`** — файл, который исполняет Cloudflare. Его создаёт `opennextjs-cloudflare build`,
   в git он не хранится. Поэтому «деплой» — это всегда «сборка + загрузка», а не «загрузить
   то, что лежит в репозитории».
3. **`compatibility_date`** — Cloudflare развивает рантайм (`workerd`), и он может менять
   поведение. Дата фиксирует «диалект»: сюрпризов от обновлений платформы не будет, пока дату
   не поднимут осознанно.
4. **`nodejs_compat`** — включает набор Node-совместимых API (нужен Next.js и OpenNext).
   Без него приложение упадёт на старте.
5. **D1-база**: `binding: "DB"` — это имя, под которым база доступна в коде (`env.DB`);
   `database_name` — человекочитаемое имя в аккаунте; `database_id` — уникальный идентификатор
   базы (`5a15f362-…`); `migrations_dir` — каталог с `.sql`-миграциями, которые применяет
   `wrangler d1 migrations apply`. `database_id` **не секрет** — см. §10.
6. **Домен**: `custom_domain: true` означает «Cloudflare сам создаст DNS-запись и сертификат под
   этот hostname и привяжет его к воркеру». Подробно — §5.3.
7. **Assets**: статика сборки отдаётся Cloudflare напрямую (быстро и дешево), не через код
   приложения. В коде она доступна как `env.ASSETS`.
8. **`WORKER_SELF_REFERENCE`** — «сервисный биндинг на самого себя»: воркер может вызывать
   самого себя. Это нужно механизму кэша OpenNext (ревалидация страниц). Поэтому пункт (1)
   и это поле должны совпадать — иначе деплой пройдёт, а кэш/ревалидация работать не будут.
9. **Observability** — включает логи и трейсы воркера в дашборде Cloudflare (см. §5.4).

Заметки к этому конфигу (почему в нём _нет_ того, что было раньше):
`r2_buckets` убраны (`MY_BUCKET` кодом не используется — остаётся заделом под сканы согласий),
`images` (биндинг `IMAGES`) не нужен — подключён собственный загрузчик `image-loader.ts`,
флаг `global_fetch_strictly_public` убран (он нужен только для same-zone global fetch, у нас не
используется), Smart Placement (`placement`) остаётся отключённым.

**Если меняешь биндинги** — перегенерируй типы для TypeScript, иначе редактор/`tsc` будут
ругаться на неизвестные поля `env`:

```bash
npm run cf-typegen     # wrangler types --env-interface CloudflareEnv ./cloudflare-env.d.ts
```

## 4. Локальный мир и прод — два разных мира

Главная ловушка новичка: **один и тот же код работает и локально, и в проде, но данные у них
разные**. Отличается ровно одно — куда указывает биндинг `DB`.

| Что                        | Локально                                  | Прод                                                          |
| -------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| Какой конфиг читается      | тот же `wrangler.jsonc`                   | тот же `wrangler.jsonc`                                       |
| Куда указывает `env.DB`    | файл SQLite в `.wrangler/state/v3/d1`     | облачная D1 `rdd` (`5a15f362-…`)                              |
| Кто «прокидывает» биндинги | `getPlatformProxy()` (wrangler), локально | Cloudflare при деплое                                         |
| Кто наполняет данные       | `db:restart`, `seed:demo`, `user:create`  | `db:migrate:remote`, `seed:demo:remote`, `user:create:remote` |
| Цена ошибки                | пересоздать базу за 10 секунд             | дамп + разбор, что потеряли                                   |
| Где физически лежит        | `.wrangler/` (в `.gitignore`)             | в аккаунте Cloudflare                                         |

Правила, чтобы не перепутать окружения:

1. **Суффикс `:remote` = прод.** `db:migrate:remote`, `seed:demo:remote`, `user:create:remote`,
   `db:restart:remote`. Команда без суффикса работает с локальной базой.
2. Все `:remote`-команды спрашивают подтверждение (напечатать `prod`) или принимают `--yes`.
3. В выводе wrangler всегда есть строка `Resource location: local` или `remote` — она и есть
   ответ на вопрос «куда я сейчас пишу».
4. `npm run db:list` (`wrangler d1 list`) показывает облачные базы — быстрый способ убедиться,
   что прод-база существует и что ты залогинен.
5. Локальную базу можно стирать сколько угодно: `npm run db:restart` (полный ресет),
   затем `npm run user:create`. Прод так стирать можно только через `db:restart:remote` (с дампом).

Про локальные команды запуска: `npm run dev` — обычный Next dev (локальная D1 через
`initOpenNextCloudflareForDev`); `npm run dev:cf` — локальный запуск в рантайме Cloudflare
(наследие Pages-подхода, `wrangler pages dev`); `npm run preview` — сборка + `wrangler dev`,
то есть максимально близкая к проду проверка Worker-а (та же мысль в README: `npm run preview`
для локального CF-рантайма).

## 5. Деплой шаг за шагом

### 5.1. Логин в Cloudflare (разово, но иногда истекает)

```bash
npx wrangler login     # откроет браузер и попросит подтвердить доступ
npx wrangler whoami    # покажет e-mail и аккаунт — проверка, что всё ок
```

Wrangler кладёт OAuth-токен **вне репозитория** (на Windows —
`%APPDATA%\xdg.config\.wrangler\config\default.toml`). Токен со временем истекает, и тогда любая
команда wrangler падает с `Failed to fetch auth token: 400 Bad Request` и `Not logged in` —
лечение одно: снова `npx wrangler login`.

Для автоматизации (например, деплой из CI) вместо OAuth используется переменная окружения
`CLOUDFLARE_API_TOKEN` с правами `workers_scripts:write`, `workers_routes:write`, `d1:write`,
`zone:read`.

### 5.2. Сборка и загрузка: `npm run deploy`

Команда состоит из двух шагов:

| Шаг | Что делает                                                                                                                                                                                                 | Сколько |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| 1   | `opennextjs-cloudflare build` — компилирует Next.js в `.open-next/worker.js` + `.open-next/assets/**`                                                                                                      | минуты  |
| 2   | `opennextjs-cloudflare deploy` → `wrangler deploy`: загружает код и статику, создаёт/обновляет воркер `rdd`, привязывает `DB`, `ASSETS`, self-reference, включает observability и применяет правила домена | секунды |

Что важно понимать:

- **Перед сборкой применяется патч OpenNext.** `npm ci` запускает `postinstall` → `scripts/patch-opennext-turbopack.ts`.
  Это обязательный шаг на Windows: без него Turbopack-сборка формально проходит, но в воркер не
  попадают SSR-чанки и **каждая** страница на проде отдаёт 500 (см. §9). Скрипт идемпотентен, так
  что вручную запускать его не нужно — достаточно обычного `npm ci`. Если `node_modules` трогали
  руками, патч мог пропасть: проверка в §9.
- Деплой создаёт **новую версию** воркера и переключает на неё трафик атомарно. Откат — на
  предыдущую версию (§8).
- **Данные D1 деплой не трогает**: миграции отдельным шагом (§5.5).
- Приложению **не нужны секреты** — ни в Cloudflare, ни в GitHub. Доступ требуется только CLI
  (см. §5.1).
- Вспомогательные команды: `npm run upload` — загрузить версию **без** переключения трафика
  (`wrangler versions upload`; удобно «примерить» изменение); `npm run preview` — собрать и
  запустить локально в CF-рантайме (`wrangler dev`).

### 5.3. Домен: как воркер получает «человеческий» адрес

Сразу после первого деплоя воркер доступен по служебному адресу
`https://rdd.<account-subdomain>.workers.dev` — он создаётся автоматически, настраивать нечего.
Красивый адрес (`rdd.ux42.studio`) — это отдельная сущность Cloudflare: **привязка hostname к
воркеру**. Есть два способа привязки:

| Способ            | Кто создаёт DNS-запись                     | Как выглядит в конфиге                                | Комментарий                                                                            |
| ----------------- | ------------------------------------------ | ----------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **Custom Domain** | Cloudflare (сам, при деплое, + сертификат) | `"pattern": "rdd.ux42.studio", "custom_domain": true` | Рекомендуется для воркеров: DNS и сертификат управляются воркером                      |
| **Route**         | Ты сам (A/AAAA/CNAME с оранжевым облаком)  | `"pattern": "rdd.ux42.studio/*"`                      | Работает, когда запись уже есть; воркер перехватывает запросы и origin не используется |

В этом проекте выбран **Custom Domain** — то есть «создание домена» происходит автоматически во
время `npm run deploy`, руками в дашборде ничего создавать не нужно.

**Типичная ошибка (и что мы с ней сделали).** Ручная DNS-запись с тем же именем **конфликтует**
с Custom Domain: Cloudflare откажется создавать привязку (ошибка вида
`A DNS record with that name already exists`). В нашем случае для `rdd.ux42.studio` была создана
ручная `CNAME rdd → ux42.studio (Proxied)` — запись-заглушка, которая никуда не ведёт. Пока
за ней не стоит воркер, браузер получает **HTTP 522** («edge не смог получить ответ от origin») —
это не поломка приложения, а «домен есть, обслуживать его пока нечем». Решение: удалить ручную
запись и дать Cloudflare создать Custom Domain при деплое (сделано).

Если домен вообще не нужен — достаточно удалить блок `routes` из `wrangler.jsonc`: воркер
останется доступен на `rdd.<account>.workers.dev`. Чтобы сменить домен — правится одна строка
`pattern` (зона нового домена должна лежать в том же аккаунте Cloudflare).

### 5.4. Проверка живого прода

```bash
curl -I https://rdd.ux42.studio     # ожидаем 200 или 302 на /login
npx wrangler deployments list       # что и когда задеплоено (версии воркера)
npx wrangler tail                   # live-логи; Ctrl+C для выхода
```

- После **первого** деплоя с новым доменом привязка и сертификат могут оформляться несколько минут.
  Если сразу видишь 522 — подожди 2–5 минут и повтори `curl`.
- В дашборде: `Workers & Pages → rdd → Deployments` (версии и время), `Settings → Domains & Routes`
  (привязка домена), логи/трейсы — из-за `observability: true`.
- Признак, что база подключена: страница `/login` открывается, а после `user:create:remote` можно
  войти (страницы читают таблицу `users`).

### 5.5. Данные на проде: три независимые команды

Деплой кода и содержимое БД разведены специально. Для прода есть три отдельные операции:

| Задача       | Команда                      | Что делает                                                                                                                                             |
| ------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Схема        | `npm run db:migrate:remote`  | Применяет `migrations/*.sql` (0001–0007) к облачной D1. Повторный запуск безопасен: применённые миграции пропускаются (учёт в таблице `d1_migrations`) |
| Пользователь | `npm run user:create:remote` | Создаёт пользователя. **Первый в базе всегда получает роль `admin`**; пароль генерируется (`--gen-password`) или вводится с клавиатуры                 |
| Демо-данные  | `npm run seed:demo:remote`   | Заливает демо-пациентов (11 пациентов с фазами). Просит подтверждение «prod» или принимает `--yes`                                                     |

Проверить результат:

```bash
npx wrangler d1 execute rdd --remote --command "SELECT name FROM d1_migrations"
npx wrangler d1 execute rdd --remote --command "SELECT COUNT(*) AS patients FROM patients"
```

⚠️ Демо-данные искажают агрегаты на странице `/reports` (они считаются по всей базе). Если нужны
«чистые» цифры — не заливайте сид либо сначала обнулите базу (§5.6).

### 5.6. Полный сброс прод-БД («как с нуля»)

Скрипт: `scripts/db-restart-remote.ts` (по аналогии с локальным `scripts/db-restart.ts`).

```bash
npm run db:restart:remote        # дамп → DROP таблиц → миграции
npm run db:restart:remote:seed   # то же + демо-данные
```

Что происходит по шагам и почему именно так:

1. **Подтверждение.** Просит напечатать `prod` (или `--yes` для автоматизации) — защита от
   случайного запуска на проде.
2. **Дамп (бэкап).** `npx wrangler d1 export rdd --remote` → `.wrangler/backups/rdd-<дата_время>.sql`,
   и печатает готовую команду восстановления. Каталог `.wrangler` в `.gitignore` — дамп содержит
   данные пациентов и в git попасть не должен. Отключить дамп: `--no-backup`.
3. **DROP всех таблиц** в порядке «дочерние → родительские». Почему порядок важен: **D1 применяет
   внешние ключи всегда** (эквивалент `PRAGMA foreign_keys = on`), а `PRAGMA foreign_keys = off`
   в D1 недоступен. Поэтому скрипт вычисляет порядок из DDL в `sqlite_master` (по `REFERENCES`),
   а не хардкодит его. Служебные таблицы движка (`sqlite_*`, `_cf_*`) исключены — их DROP даёт
   `not authorized: SQLITE_AUTH`. Таблица `d1_migrations` удаляется намеренно: иначе wrangler
   решит, что миграции уже применены, и схема останется пустой.
4. **Миграции.** `npx wrangler d1 migrations apply rdd --remote` — пересоздаёт схему и заново
   записывает 0001–0007 в `d1_migrations`.
5. **Проверка.** Скрипт убеждается, что все обязательные таблицы на месте (`patients`, `phases`,
   `registry_versions`, `users`, `sessions`, `invites`, `audit_log`) и применено 7 из 7 миграций;
   при расхождении — падает с ошибкой (а не оставляет полупустую базу).
6. **`--seed`** (необязательно) — запускает сеялку: `seed-demo.ts --remote`.

После сброса **все пользователи и сессии удалены**: войти в прод нельзя, пока не создадите админа —
`npm run user:create:remote`.

Флаги: `--yes` (без интерактивного подтверждения), `--seed` (с демо-данными), `--no-backup`,
`--local` (прогон по локальной БД — только для отладки самого скрипта, прода не касается).

Восстановление из дампа (если понадобилось):

```bash
npx wrangler d1 execute rdd --remote --yes --file=".wrangler/backups/rdd-2026-09-21_22-27-00.sql"
```

Дамп содержит `CREATE TABLE` + `INSERT`, поэтому его надо накатывать на **пустую** базу
(например, после сброса с `--no-backup`). Если сброс случился в последние 30 дней, есть более
простой путь — откат всей базы средствами Cloudflare, см. §8.

## 6. CI (GitHub Actions): зачем нужен и как устроен

### 6.1. Почему это не «замена» Cloudflare, а другой инструмент

|                   | Cloudflare (wrangler/OpenNext)                                                                            | GitHub Actions (CI)                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Что делает        | Доставка и рантайм: сборка-загрузка, версии воркера, атомарное переключение, домен и сертификат, логи, D1 | Проверки кода: `lint`, типы, границы FSD, unit- и интеграционные тесты |
| Чего не делает    | Не знает про FSD, не запускает vitest, не сверяет `package.json` с `package-lock.json`                    | Не деплоит прод (по умолчанию)                                         |
| Когда срабатывает | Когда ты сам запустил `npm run deploy`                                                                    | На каждый push в `main` и на каждый Pull Request                       |

Хороший пример, почему нужны оба: в проекте как-то раз уехал неполный `package-lock.json`
(в нём не хватало `esbuild@0.28.2`). Локально всё «работало» — `npm install`/`npm ci` на npm 11
проблему проглатывал, и `npm run deploy` проходил. А CI (с npm 10 на Node 22) падал **на первом же
шаге** с `EUSAGE`, и все проверки после него просто не выполнялись. То есть красный CI был
единственным сигналом о реальной поломке воспроизводимости установки.

### 6.2. Разбор `.github/workflows/ci.yml`

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5 # 1. скачать репозиторий
      - uses: actions/setup-node@v5 # 2. поставить Node и кэш npm
        with:
          node-version: 24
          cache: npm
      - run: npm ci # 3. установка строго по package-lock.json
      - name: Lint # 4. ESLint
        run: npm run lint
      - name: Typecheck # 5. TypeScript
        run: npx tsc --noEmit
      - name: FSD layers (steiger) # 6. границы слоёв FSD
        run: npm run steiger
      - name: Unit tests # 7. tests/unit (без БД)
        run: npx vitest run
      - name: Integration tests (local D1) # 8. tests/integration на локальной D1
        run: npm run test:db
```

Что ловит каждый шаг:

| Шаг                | Что проверяет                                                    | Пример дефекта                                               |
| ------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------ |
| `npm ci`           | Совпадение `package.json` и `package-lock.json`                  | Неполный lockfile (`Missing: esbuild@0.28.2 from lock file`) |
| `npm run lint`     | Стиль и подозрительный код (0 ошибок; warnings не роняют сборку) | Любая ошибка ESLint                                          |
| `npx tsc --noEmit` | Типы по всему проекту (включая `scripts/`)                       | Опечатка в имени поля реестра                                |
| `npm run steiger`  | Архитектурные границы FSD (кто кого может импортировать)         | Импорт из `widgets` внутрь `entities`                        |
| `npx vitest run`   | Логика без БД (`tests/unit`, 22 файла)                           | Сломанная валидация/CAS-логика                               |
| `npm run test:db`  | SQL-репозитории и схема на локальной D1 (`tests/integration`)    | Неверный запрос, отсутствующая колонка                       |

Про Node 24 и actions `@v5`: GitHub раньше выдавал предупреждение
`Node.js 20 is deprecated … actions/checkout@v4, actions/setup-node@v4` — потому что рантайм
самих actions старый. Мажоры `v5`+ объявляют рантайм `node24`, поэтому в workflow стоят `@v5`
(первый мажор без изменения поведения). Node 24 — актуальный LTS; вместе с ним приходит npm 11,
то есть локальная и CI-установка идут на одной мажорной версии npm.

Важная деталь: CI работает на **чистой** машине, поэтому интеграционные тесты там видят пустую
базу. Локально база обычно не пустая (демо-данные) — см. §9, пункт про агрегаты.

### 6.3. Правило про lockfile (чтобы CI не краснел на ровном месте)

1. Меняешь зависимости — коммить **оба** файла: `package.json` и `package-lock.json`.
2. Локальная проверка — тем же способом, что в CI: **`npm ci`** (не `npm install`). `npm ci`
   удаляет `node_modules` и ставит строго по lockfile — именно так проверяется воспроизводимость.
3. Если `npm ci` падает с `EUSAGE … Missing: X from lock file` — lockfile неполный:
   почини `npm install --package-lock-only` и закоммить результат.
4. Держи локальный Node/npm в той же мажорной линии, что CI (сейчас стоит цель «CI = Node 24 =
   npm 11»). npm другой мажорной версии может «не заметить» то, что CI считает ошибкой —
   ровно так и возник случай с `esbuild` выше.
5. Никогда не правь `package-lock.json` руками и не удаляй его из репозитория: он и есть гарантия,
   что у всех (и в CI, и на проде) одинаковые версии зависимостей.

### 6.4. Как читать красный CI и почему он не деплоит

- На странице рина (`GitHub → Actions`) видно, какой шаг упал: шаги ниже помечаются `skipped`.
  Это важный сигнал: если упал `npm ci`, то **никакие** тесты не запускались, то есть «зелёной
  сборки» не было вообще.
- Воспроизведение локально: те же команды в том же порядке. Для интеграционных тестов помни
  правило «пустой базы» (§9, пункт про агрегаты).
- **CI ничего не деплоит.** Зелёный CI означает «код проверен», а не «прод обновлён». Прод
  обновляется только вручную: `npm run deploy`. Так задумано (осознанно: демо разворачивается из
  локального окружения, см. [spec-stage-4.md](./spec-stage-4.md) §4) — и это же описано в
  [nfr.md](./nfr.md): «деплой ручной», RTO не гарантируется, аварийный путь — пере-деплой из Git.
- Если позже захочешь автодеплой: в тот же workflow добавляется job `deploy`, который выполняется
  после `ci` и вызывает `npm run deploy` с секретом `CLOUDFLARE_API_TOKEN`. Тогда «руками»
  остаётся только аварийное вмешательство.

## 7. Типичные сценарии: что делать, когда…

### 7.1. Изменил код (UI, логику, запросы)

```bash
npm ci && npm run lint && npx tsc --noEmit && npx vitest run   # или просто npm run test
git add -A && git commit -m "…" && git push                    # CI проверит
npm run deploy                                                 # прод обновится
```

### 7.2. Изменил реестр полей (добавил/переименовал поле)

Реестр — источник правды, схема генерируется из него ([schema-evolution.md](./schema-evolution.md)):

```bash
npm run gen:d1          # перегенерировать миграции из реестра
npm run db:restart      # пересоздать локальную БД и проверить, что всё применяется
npm run test            # и что код не сломался
git add -A && git commit -m "…" && git push
npm run deploy          # код в прод (схема прода пока старая)
npm run db:migrate:remote   # схема прода: применить новые миграции
```

Порядок «код → миграция» выбран сознательно: старый код со старой схемой работает, а новый код
без новой колонки — нет. Если наоборот (сначала схема), то окно между шагами ломает прод.

### 7.3. Хочу чистый прод с демо-данными (для показа)

```bash
npm run db:restart:remote:seed    # дамп → DROP → миграции → 11 демо-пациентов
npm run user:create:remote        # обязательный шаг: пользователи удалены вместе с базой
```

### 7.4. Меняю домен или отказываюсь от него

- другой домен: правка `pattern` в `wrangler.jsonc` → `npm run deploy` (зона должна быть в том же
  аккаунте Cloudflare);
- совсем без домена: удалить блок `routes` → `npm run deploy`; воркер останется на
  `rdd.<account>.workers.dev`;
- сменил домен — старые сессии/куки остаются привязаны к старому hostname, это ожидаемо.

### 7.5. Добавляю новый биндинг (например, R2 под сканы согласий)

1. объявить биндинг в `wrangler.jsonc` (аналогично `d1_databases`);
2. перегенерировать типы: `npm run cf-typegen` (иначе `tsc` не увидит новое поле в `env`);
3. использовать в коде (`env.MY_BUCKET`), дописать тесты;
4. `git push` → CI; `npm run deploy`.

Задел уже описан в [consent.md](./consent.md) (создание R2-бакета и авторизованное скачивание —
за границами демо).

## 8. Откат и восстановление (что делать, если сломалось)

### 8.1. Откат кода (воркера)

```bash
npx wrangler deployments list                        # последние 10 деплоев: id, дата, автор
npx wrangler deployments status                       # что сейчас обслуживает прод
npx wrangler rollback                                 # вернуться к предыдущей версии
npx wrangler rollback <version-id> -m "причина отката" # к конкретной версии
```

Откат кода **не меняет данные** в D1. Если «сломался» не код, а схема/данные — см. 8.2.

### 8.2. Восстановление данных D1

Три уровня, от «быстро и точно» к «грубо, но надёжно»:

| Способ                                         | Когда применим                                    | Как                                                                                                                                                    | Ограничения                                                                                                                                                                                                |
| ---------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Time Travel** (встроен в D1)                 | «случайно испортили данные» минуты-дни назад      | `npx wrangler d1 time-travel info rdd` → bookmark; затем `npx wrangler d1 time-travel restore rdd --bookmark=<…>` (или `--timestamp=<unix / RFC3339>`) | История: **30 дней** на Workers Paid, **7 дней** на Workers Free. Восстановление **перезаписывает базу целиком**, запросы «в полёте» обрываются; в ответе даётся bookmark для отмены самого восстановления |
| **Дамп из `.wrangler/backups/`**               | Есть свежий дамп (его делает `db:restart:remote`) | `npx wrangler d1 execute rdd --remote --yes --file="<дамп>"`                                                                                           | В дампе есть `CREATE TABLE`, поэтому накатывать на **пустую** базу                                                                                                                                         |
| **Полный сброс** (`npm run db:restart:remote`) | Нужно гарантированно чистое состояние             | см. §5.6                                                                                                                                               | Данные теряются (остаётся дамп), пользователей надо создавать заново                                                                                                                                       |

Time Travel не нужно включать и отдельно оплачивать. Поддерживается ли база — видно по
`npx wrangler d1 info rdd`: `version: production` — новый Time Travel API, `version: alpha` —
старые снапшоты (для баз, созданных очень давно).

### 8.3. «Прод лежит» — порядок разбора

1. `curl -I https://rdd.ux42.studio` — понять, что именно отвечает (код и наличие `cf-ray`).
2. `npx wrangler tail` — смотреть ошибки воркера в реальном времени.
3. `npx wrangler deployments list` и дашборд (`Deployments`) — не было ли свежего деплоя/миграции.
4. Дальше по симптому: код → `wrangler rollback`; данные → Time Travel; домен → §9.

Связь с NFR: демо **не даёт гарантий** доступности, RTO/RPO не зафиксированы, регулярных бэкапов
и плана восстановления нет — это осознанно вынесено за рамки (см. [nfr.md](./nfr.md) §1–2 и
«Backup / DR» в [architecture-overview.md](./architecture-overview.md)). Всё, что описано выше, —
это то, чем реально можно воспользоваться, а не SLA.

| Локально падают интеграционные тесты агрегатов (`expected 34 to be 2`)                                                                                          | Локальная БД не пустая — демо-данные искажают агрегаты                                                                                                                                                                                                                                                                                                                                                       | `npm run db:restart` перед `npm run test:db`; в CI база пустая, поэтому там зелено ([spec-stage-4.md](./spec-stage-4.md) §3)                                                                                                                                                                                                                                                                                              |

| В `npm run dev` нет `env.DB`                                                                                                                                    | Не инициализированы bindings для dev-режима                                                                                                                                                                                                                                                                                                                                                                  | Проверить `initOpenNextCloudflareForDev()` в `next.config.ts` и наличие `wrangler.jsonc`                                                                                                                                                                                                                                                                                                                                  |
| Прод отдаёт 500 сразу после деплоя                                                                                                                              | Обычно рассинхрон кода и схемы либо расхождение имени воркера и self-reference                                                                                                                                                                                                                                                                                                                               | `npx wrangler tail`; сверить `name` == `services[].service`; при необходимости `npx wrangler rollback`                                                                                                                                                                                                                                                                                                                    |
| Деплой на Windows падает: `Missing file or directory: …\resvg.wasm?module`                                                                                      | Старый `wrangler` (< 4.141) пишет wasm-модуль с суффиксом `?module` в имени файла, а в Windows символ `?` в имени файла недопустим. На Linux/CI баг невидим                                                                                                                                                                                                                                                  | Обновить dev-зависимость: `npm i -D wrangler@^4.141.0` (правится `package.json` + `package-lock.json`); проверить `npx wrangler deploy --dry-run`                                                                                                                                                                                                                                                                         |
| `EPERM` / `EBUSY` при `npm run db:restart` или при сборке `.open-next`                                                                                          | Локальный dev-сервер (`npm run dev` / `dev:cf`, workerd) держит файлы `.wrangler/state/v3/d1` и `.open-next`                                                                                                                                                                                                                                                                                                 | Сначала остановить dev-сервер (`Ctrl+C`, при необходимости снять процессы `node.exe`/`workerd.exe`), затем повторить команду. Если `.open-next` не удаляется — `rmdir .open-next\assets` (на Windows это junction)                                                                                                                                                                                                        |
| **Все** маршруты на проде отдают 500, в логе `ChunkLoadError: Failed to load chunk server/chunks/ssr/…` или `components.ComponentMod.handler is not a function` | **Windows-баг OpenNext + Turbopack.** Плагин `patches/plugins/turbopack.js` фильтрует traced-файлы строкой `file.includes(".next/server/chunks/")` и переписывает путь через `chunk.replace(/.*\/\.next\//, "")` — оба ожидают POSIX-слеши, а на Windows пути приходят с обратными. Итог: `switch` в `requireChunk()` пустой, SSR-чанки не инлайнятся, любая страница падает. На Linux/CI не воспроизводится | Проверить, что патч применён: `npx tsx scripts/patch-opennext-turbopack.ts` → должно быть `✅ Патч OpenNext (Windows, traced-файлы) применён`, а в плагине `grep -c "rdd:patch:win-traced-files" node_modules/@opennextjs/cloudflare/dist/cli/build/patches/plugins/turbopack.js` → `1`. Затем **пересобрать** (`rm -rf .next .open-next && npm run deploy`) и задеплоить. Скрипт идемпотентен, повторный вызов безвреден |
| Тот же 500, но патч применён (маркер = 1)                                                                                                                       | Патч правит только пути; сборка должна идти **после** его применения. Типичная ошибка — `npm ci`/`npm install` переустановил `node_modules` и затёр патч, а деплой пошёл на старом `.open-next`                                                                                                                                                                                                              | Порядок: `npm ci` → (postinstall сам применит патч) → `rm -rf .next .open-next` → `npm run deploy`. Проверить, что в `.open-next/server-functions/default/handler.mjs` есть `case "chunks/ssr/…` — это признак, что чанки реально инлайнятся                                                                                                                                                                              |
| Официального патча OpenNext ещё нет — нужен обходной путь                                                                                                       | Ожидаемо: патч живёт в `node_modules` и переживает только `npm ci`. Альтернатива — webpack вместо Turbopack: `"build": "next build --webpack"` в `package.json`                                                                                                                                                                                                                                              | Обе стратегии рабочие. Turbopack + патч быстрее и остаётся путём по умолчанию; webpack вообще не зависит от этого бага, но медленнее и требует, чтобы `'use client'` компоненты **не** импортировали серверные модули (`node:crypto` и т. п.) — иначе `UnhandledSchemeError: Reading from "node:crypto"`                                                                                                                  |
| Скрипты падают: `Unexpected non-whitespace character after JSON at position …`                                                                                  | Начиная с `wrangler` 4.141 вывод `d1 execute --json` — **массив** `[{…}]`, а не объект `{…}`. Парсер, ищущий первую `{` и парсящий до конца, падает на закрывающей `]`                                                                                                                                                                                                                                       | Парсить оба формата (как в `scripts/seed-demo.ts` и `scripts/db-restart-remote.ts`). При отладке — `npx wrangler d1 execute rdd --remote --json --command "SELECT …" \| head` и смотреть первую строку: `[` или `{`                                                                                                                                                                                                       |
| Верификация записи в БД не проходит, хотя запись создана                                                                                                        | `wrangler d1 execute --file=…` в ответе отдаёт **сводку** (`Total queries executed`, `Rows read`), а не строки `SELECT` — проверять по нему нечего                                                                                                                                                                                                                                                           | Проверочный `SELECT` выполнять через `--command "SELECT …"`, а не `--file`. Тот же приём в `scripts/create-user.ts`                                                                                                                                                                                                                                                                                                       |
| CI красный на `steiger`/`tsc`, а локально «работало»                                                                                                            | Другая версия Node/npm или незакоммиченные файлы                                                                                                                                                                                                                                                                                                                                                             | Повторить команды в том же порядке и на той же версии Node (см. §6.3)                                                                                                                                                                                                                                                                                                                                                     |

Общее правило: **сначала понять, на каком уровне сбой** — код воркера, привязка домена, доступ к
аккаунту или данные. Это независимые контуры, и лечится каждый своей командой.

## 10. Секреты и чувствительные данные

**Приложению секреты не нужны.** В коде нет ни API-ключей, ни обращений к внешним сервисам:
доступ к базе — через биндинг `DB`, к статике — через `ASSETS`. Отсюда:

- в GitHub нет секретов для сборки и тестов;
- в Cloudflare нет рантайм-секретов (`wrangler secret put` не используется);
- `.dev.vars*` лежит в `.gitignore` (понадобится только если появятся секреты).

**Что секретом НЕ является** (и правильно, что лежит в репозитории):

| Данные                       | Почему это не секрет                                                                                                                                                                                     |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `database_id` (`5a15f362-…`) | Это идентификатор базы, а не ключ доступа: без токена аккаунта он бесполезен — D1 доступна только через bindings воркера в твоём аккаунте. Он и так виден в дашборде, в логах `wrangler` и в вызовах API |
| Имя воркера, домен, роуты    | Публичная информация (резолвится через DNS, видна любому)                                                                                                                                                |

**Что действительно секрет и где ему место:**

| Секрет                                     | Где хранится                                                          | Чего делать нельзя                         |
| ------------------------------------------ | --------------------------------------------------------------------- | ------------------------------------------ |
| OAuth-токен wrangler                       | Вне репозитория, `%APPDATA%\xdg.config\.wrangler\config\default.toml` | Коммитить, пересылать в чат                |
| `CLOUDFLARE_API_TOKEN` (для автоматизации) | Переменная окружения / секреты CI                                     | Хардкодить в скрипты и в `wrangler.jsonc`  |
| Пароли пользователей                       | В БД, только PBKDF2-хэши (см. [auth.md](./auth.md))                   | Логировать пароли, хранить в открытом виде |
| Дампы БД                                   | `.wrangler/backups/` (каталог в `.gitignore`)                         | Коммитить дампы: там данные пациентов      |

Если токен всё же попал в git — сначала **отозвать** его в дашборде (`My Profile → API Tokens`),
и только потом чистить историю: отзыв действует мгновенно, а удаление коммита — нет.

## 11. Чек-листы

### 11.1. Первый деплой (с нуля)

```bash
npx wrangler login                                  # 1. доступ к аккаунту
npx wrangler whoami                                 # 2. проверка: виден аккаунт
npx wrangler --version                              # 3. должно быть >= 4.141 (см. §9 про Windows)
npm ci                                              # 4. зависимости по lockfile (postinstall сам применит патч OpenNext, см. §5.2/§9)
npm run deploy                                      # 5. сборка + загрузка + создание Custom Domain
curl -I https://rdd.ux42.studio                     # 6. ждём 200/302 (сертификат может занять минуты)
npm run db:migrate:remote                           # 7. схема прод-Д1
npm run user:create:remote                          # 8. первый админ
npm run seed:demo:remote                            # 9. (опционально) демо-данные
```

Перед `npm run deploy` **обязательно остановите локальный dev-сервер** (`npm run dev`,
`npm run dev:cf`): он держит `.wrangler/state/v3/d1` и `.open-next`, и сборка падает с
`EPERM`. Шаг 3 нужен на Windows: на `wrangler` < 4.141 деплой падает с
`Missing file or directory: …\resvg.wasm?module` (см. §9).

Ещё одно Windows-специфичное условие: патч OpenNext из шага 4 обязателен, иначе сборка
пройдёт, а **каждая** страница на проде будет отдавать 500 (`ChunkLoadError`) — это самая
неочевидная поломка в цепочке, потому что `npm run deploy` завершается успешно (см. §5.2 и §9).

Признаки успеха: в дашборде появился воркер `rdd` и домен `rdd.ux42.studio` (Domains & Routes);
`curl` отдаёт 200/302; вход на `/login` работает.

### 11.2. Обычный релиз

```bash
npm ci && npm run test && npm run lint && npx tsc --noEmit && npm run steiger   # локально
git push                                                                        # CI проверит
# дождаться зелёного CI
npm run deploy                                                                  # выкатить прод
curl -I https://rdd.ux42.studio                                                 # проверить
```

### 11.3. Перед любой операцией с прод-данными

1. Убедиться, что будет дамп (`db:restart:remote` делает его сам; иначе — `npx wrangler d1 export`).
2. Помнить, что после сброса пользователей нет → сразу запланировать `user:create:remote`.
3. После операции проверить `SELECT COUNT(*)` по ключевым таблицам и открыть `/login`.

### 11.4. Аварийное восстановление (в терминах [nfr.md](./nfr.md))

Демо не даёт SLA, поэтому «план» такой: клон репозитория → `npm ci` → `npm run deploy` →
`npm run db:migrate:remote` (если база пустая) либо восстановление данных через Time Travel/дамп.
RTO ≤ 4 ч и RPO ≤ 1 ч — это **целевые** значения прод-версии, а не текущие гарантии.

## 12. Глоссарий

| Термин                                       | Простыми словами                                                                                          |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Worker                                       | Изолированная JS-программа, которую Cloudflare исполняет на своей сети. Наш воркер называется `rdd`       |
| `wrangler`                                   | CLI Cloudflare: логин, деплой, работа с D1, логи. Запускается как `npx wrangler …` или из npm-скриптов    |
| OpenNext (`opennextjs-cloudflare`)           | Инструмент, превращающий приложение Next.js в Worker                                                      |
| Binding (биндинг)                            | «Провод» от воркера к внешнему ресурсу (база, статика). Объявляется в `wrangler.jsonc`, в коде — `env.DB` |
| D1                                           | Облачная база Cloudflare (SQLite). У нас — база `rdd`, id `5a15f362-…`                                    |
| Assets                                       | Статика воркера: файлы, которые Cloudflare отдаёт напрямую (в коде `env.ASSETS`)                          |
| Custom Domain                                | Привязка своего домена к воркеру, при которой Cloudflare сам создаёт DNS-запись и сертификат              |
| Route                                        | Правило «запросы какого hostname передавать воркеру»; DNS-запись при этом создаёшь ты сам                 |
| Version / Deployment                         | Версия кода воркера и факт того, что именно она обслуживает трафик; деплой = новая версия + переключение  |
| `rollback`                                   | Откат на предыдущую версию воркера (данные не затрагиваются)                                              |
| Bookmark / Time Travel                       | Встроенная «машина времени» D1: точки восстановления базы (30 дней на Paid, 7 дней на Free)               |
| Суффикс `:remote`                            | Признак того, что команда работает с продом, а не с локальной базой                                       |
| `.open-next/`                                | Каталог сборки (в git не хранится): точка входа воркера и статика                                         |
| `compatibility_date` / `compatibility_flags` | Настройки «диалекта» рантайма Cloudflare: фиксируют поведение и включают Node-совместимость               |
| Self-reference binding                       | Биндинг воркера на самого себя (`WORKER_SELF_REFERENCE`), нужен кэшу OpenNext                             |
| Lockfile (`package-lock.json`)               | Точный список версий зависимостей; `npm ci` ставит строго по нему                                         |
| CI                                           | GitHub Actions: прогон проверок на push/PR. Деплой не выполняет                                           |

См. также: [nfr.md](./nfr.md) (Availability, RTO/RPO), [schema-evolution.md](./schema-evolution.md)
(эволюция схемы), [spec-stage-4.md](./spec-stage-4.md) §4 (история решений по CI),
[architecture-overview.md](./architecture-overview.md) (границы демо, «Backup / DR»),
[auth.md](./auth.md) (`user:create:remote`, роли), README (быстрый старт).
