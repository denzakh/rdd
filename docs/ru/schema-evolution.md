# Спецификация: Версионирование протокола и эволюция схемы (./schema-evolution.md)

**Статус:** спека · **Зависимости:** registry core (готово), gen:d1 diff-генератор (готово)
**Слой FSD:** `src/shared/config/registry`, `src/shared/lib/registry/*`; версионность протокола — в генерируемом baseline `0001_init.sql` (отдельной `000N`-миграции нет)

---

## 1. Контекст и ограничения

Реестр — единственный источник правды (rdd-v1.md §3), а `gen:d1` умеет безопасный
`ADD COLUMN`/`RENAME COLUMN` (rdd-v1.md §5). Но набор пациентов в реальном исследовании
не одномоментен: протокол (CRF) меняется по ходу набора — правкой этического комитета
добавляется шкала, у существующего поля меняется набор `options`, поле выводится из
употребления. Проблема не техническая (миграция схемы уже решена), а **семантическая**:
что означает значение поля, введённое до правки, при последующем статистическом анализе
вместе со значениями, введёнными после?

Ключевое ограничение: **`gen:d1` не знает и не должен знать о версионности** — это
осознанно оставлено за пределами diff-движка (см. §8.1 ниже), иначе схема генератора
раздувается сама на себя.

## 2. Рассмотренные варианты (решения)

| Вариант                                                                               | Решение                                                                                                                                             |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. `registry_version` на записи (пациент/фаза «заморожены» под версией на дату сбора) | **ПРИНЯТО** — минимальная схема, совместимо с append-only аудитом, не требует переписывания исторических данных                                     |
| B. Полная запись в отдельную таблицу истории схемы (event sourcing на уровне полей)   | отклонено: избыточно для масштаба ~50 полей/одного центра; усложняет каждый SELECT JOIN'ом на историю                                               |
| C. Миграция значений «на лету» при каждой правке (перекодирование старых данных)      | отклонено как правило по умолчанию — теряется прослеживаемость «что реально ответил врач в момент осмотра»; допустимо только как явное решение (§5) |
| D. Запрет любых семантических изменений, только форвард-совместимые добавления полей  | отклонено как единственная стратегия: реальные протоколы требуют amendment'ов у существующих полей, запрет не масштабируется на весь жизненный цикл |
| E. Версионирование всего реестра целиком (`REGISTRY_V1`, `REGISTRY_V2`, ...)          | отложено — избыточно, пока правки затрагивают единичные поля, а не структуру целиком; кандидат при систематических protocol amendment'ах            |

## 3. Классификация изменений реестра

Не любая правка реестра требует версионирования — классификация определяет, какие
изменения безопасны сами по себе (уже покрыты diff-генератором), а какие требуют
явного протокола эскалации по этой спеке:

| Тип изменения                                            | Совместимость               | Механизм                                                                                                       |
| -------------------------------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Новое поле добавлено                                     | forward-compatible          | `gen:d1 ADD COLUMN`, старые записи получают `NULL` — ничего не требуется                                       |
| Поле переименовано (тот же смысл, другой `id`/`label`)   | forward-compatible          | `gen:d1 RENAME COLUMN` — ничего не требуется                                                                   |
| У `select`-поля добавлена новая опция (`options`)        | forward-compatible          | ничего не требуется, старые коды остаются валидны                                                              |
| У `select`-поля удалена/переименована существующая опция | **breaking**                | требует `registry_version` (§4) — иначе старые коды нечитаемы                                                  |
| Изменён диапазон `min`/`max` в сторону сужения           | **breaking**                | требует `registry_version` — исторические значения могли выходить за новый диапазон                            |
| Поле выведено из употребления (protocol amendment)       | **breaking**                | поле помечается `deprecated_since: <version>`, не удаляется из реестра (см. §6.1)                              |
| Смена `db_type` существующего поля                       | **экзотическое, вне scope** | `gen:d1` уже абортируется (rdd-v1.md §5) — ручное вмешательство обязательно вне зависимости от версионирования |

### 3.1. Кто и как проставляет `deprecated_since`

`deprecated_since` — не вычисляется, а **решение человека**, проставляемое вручную в
определении поля в момент protocol amendment, тем же способом, что `label`/`options`:

```typescript
{
  id: 'ad_efficacy',
  options: { 1: 'Полный эффект', 2: 'Частичный', 3: 'Без эффекта' },
  deprecated_since: 3,          // проставляется вручную при breaking-правке
  replacedBy: 'ad_efficacy_v2', // опционально — подсказка в UI/словаре
}
```

Система не может сама «понять», что смысл шкалы изменился клинически — это вопрос
семантики протокола, не структуры кода (тот же принцип, что у abort'а `gen:d1` на
экзотических изменениях, rdd-v1.md §5). Риск — не техническая невозможность, а
человеческий фактор: правку `options` можно внести, забыв проставить флаг. Это
закрывается не «умной» автоматикой, а guard-тестом на diff реестра (по аналогии с
существующей проверкой синхронности `d1-schema.ts`/`.schema-snapshot.json`,
stage-4 §2): если у поля исчезла опция, сузился диапазон, **или появилась граница
там, где её раньше не было** (`min`/`max` был `undefined`, стал конкретным числом —
это тоже сужение, только с открытой стороны), а `deprecated_since` не увеличился —
тест в CI падает с указанием, что нужно либо завести новое поле (§5, путь 1), либо
явно задекларировать версию.

**Механика базирования на снапшоте.** Guard сравнивает поле с зафиксированным в
`.registry-evolution-snapshot.json` состоянием и требует **роста `deprecated_since`
относительно снапшота**, а не «свежести» самого файла снапшота. Снапшот не обязан
перегенерироваться при каждой легальной (forward-compatible) правке — только при
breaking-правках, когда `deprecated_since` действительно меняется. Это осознанно
слабее требования «снапшот всегда актуален»: снижает трение в CI (не нужно
перегенерировать baseline на каждый безобидный `ADD COLUMN`), но не теряет защиту —
именно `deprecated_since` относительно снапшота, а не сам факт устаревания файла,
является сигналом «эта breaking-правка была продекларирована явно».

## 4. Схема данных (в генерируемом baseline `0001_init.sql` — реестр-колонки, добавляемые `gen:d1`; ручные `0002_audit.sql`…`0007_export_throttle.sql` лежат вне реестра)

```sql
CREATE TABLE registry_versions (
  version     INTEGER PRIMARY KEY,        -- монотонно возрастающий номер протокола
  effective_at TEXT NOT NULL,             -- ISO, с какого момента действует
  note        TEXT NOT NULL,              -- краткое описание правки (protocol amendment N)
  approved_by TEXT                        -- ссылка на решение этического комитета (текстом, вне scope системы)
);

ALTER TABLE patients ADD COLUMN registry_version INTEGER NOT NULL DEFAULT 1
  REFERENCES registry_versions(version);
ALTER TABLE phases   ADD COLUMN registry_version INTEGER NOT NULL DEFAULT 1
  REFERENCES registry_versions(version);
```

- `registry_version` проставляется **один раз при создании** записи (patient/phase) и не
  меняется задним числом — так же, как `updated_at` не переписывает историю, а фиксирует
  момент. Это прямое продолжение принципа CAS/аудита (matrix.md §6.2, §6.6): данные несут
  метку контекста, в котором были собраны, а не подгоняются под текущее состояние схемы.
- Таблица и колонки живут в baseline `0001_init.sql`, который `gen:d1` рендерит из реестра
  (`src/shared/lib/registry/d1-schema.ts`: `REGISTRY_VERSIONS_SEED` + системная колонка
  `registry_version`), поэтому отдельной ручной миграции под версионность нет —
  она применяется при ресете БД (`npm run db:restart`, auth.md §10).

## 5. Изменение `options` breaking-типа (перекодирование)

Если правка breaking (§3), допустимы два пути — выбор фиксируется в самой правке
реестра, а не глобальным правилом:

1. **Новое поле** (`ad_efficacy_v2` рядом со старым `ad_efficacy`, старое помечено
   `deprecated_since`) — данные не переписываются, обе колонки читаемы по отдельности
   с учётом `registry_version` записи. Предпочтительный путь для клинических шкал.
2. **Явная миграция значений** с картой перекодирования
   (`{ old_code: new_code }` в самой правке реестра, применяется одноразовым скриптом
   только к записям с `registry_version < N`; сам скрипт-инструмент пока **не реализован** —
   путь зафиксирован, но в демо потребности не возникало) —
   допустимо для чисто технических правок (опечатка в кодировании), **запрещено** для
   изменений клинического смысла шкалы (там годится только путь 1).

## 6. Data Dictionary и экспорт под версионностью

- `data-dictionary.md`: страница `/data-dictionary` показывает актуальную версию реестра;
  `deprecated_since`-поля отображаются с пометкой **«устарело с версии N»** и ссылкой
  на `replacedBy`, если указан. **Диапазон** активности поля (например, «активно в
  версиях 1–2») не выводится: у полей нет собственного `introducedIn`, все поля реестра
  по умолчанию существуют с версии 1, поэтому нижняя граница диапазона неинформативна.
  Если в будущем появится поле, добавленное не с версии 1 (собственная «дата рождения»),
  тогда стоит завести `introducedIn` и показывать полный диапазон — сейчас это не нужно.
  Словарь остаётся синхронным источником правды и для устаревших полей.
- `export.md`: `getDeidentifiedDataset()` включает `registry_version` записи в выгрузку
  (`meta.registryVersions`) — обязательное поле для биостатистика, иначе смешение кодов
  разных версий одной шкалы в одной колонке даёт статистический артефакт, который никто
  не заметит без явной метки.

### 6.1. Жизненный цикл поля в интерфейсе (матрица)

Видимость/редактируемость зависит не от глобального флага «показывать/скрывать», а от
сравнения `record.registry_version` (пациент/фаза) с `field.deprecated_since` — та же
метка контекста из §4, применённая теперь и к рендеру, не только к экспорту:

| Случай                                                              | Поведение в гриде                                                                                                               |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Новая запись, `registry_version ≥ deprecated_since`                 | Колонка не рендерится вовсе — то же условие, что уже есть для scope/`is_current_only` (matrix.md), только по версии             |
| Старая запись, `registry_version < deprecated_since`, значение есть | Видно, **read-only** (приглушённый стиль + тултип «устарело с версии N, см. `replacedBy`»); новые значения в шкалу не вносятся  |
| Старая запись, значение отсутствует                                 | Пустая ячейка, тот же read-only, без данных                                                                                     |
| Исправление ошибки в исторических данных                            | Не через ячейку грида — отдельный узкоролевой путь с обязательным аудитом (переиспользует §5, путь 2, на масштабе одной записи) |

`isEditable = canWrite(user) && !isDeprecatedForRecord(field, record.registry_version)` —
вторая независимая ось поверх уже существующей ролевой проверки (auth.md §8), не замена ей.

## 8. Границы и пороги эскалации

### 8.1. Что осознанно не делается сейчас

- Автоматическая генерация UI для сравнения версий поля («что изменилось в протоколе v3
  относительно v2») — не реализуется, пока правок немного; `registry_versions.note`
  достаточно как текстовый журнал.
- `gen:d1` не участвует в версионировании значений — знает только про эволюцию _схемы_
  (колонки), не про эволюцию _смысла_ значений внутри колонки. Смешивать эти два
  механизма — источник будущих ошибок, граница проведена намеренно.

### 8.2. Порог эскалации к варианту E (версионирование всего реестра)

Пересмотреть решение (перейти к `REGISTRY_V1`/`REGISTRY_V2` как отдельным объектам),
если наступит хотя бы одно из:

- число breaking-правок превысит ~5–7 (порознь отслеживаемые поля становится сложнее
  держать в голове, чем цельные версии реестра);
- появится необходимость одновременно поддерживать ввод данных **по двум активным
  версиям протокола** (многоцентровое исследование, где центры переходят на amendment
  не синхронно) — сейчас `registry_version` — метка для чтения задним числом, не
  переключатель активного UI для ввода.

## 9. Критерии приёмки

1. Добавление нового `select`-поля с `options` не требует записи в `registry_versions` —
   форвард-совместимо по определению (§3).
2. Breaking-правка существующего `select`-поля без создания новой версии/нового поля —
   блокируется на ревью чек-листом (§3), а не только соглашением.
3. Guard-тест (§3.1) падает, если у поля исчезла опция/сузился диапазон, а
   `deprecated_since` не проставлен или не увеличен.
4. Экспорт (`export.md`) содержит `registry_version` для каждой строки; смешение кодов
   разных версий одной шкалы без метки — недопустимо и проверяется тестом на выгрузке
   синтетических данных с двумя версиями.
5. `/data-dictionary` показывает `deprecated_since` для выведенных из употребления полей,
   не удаляет их из отображения молча.
6. В гриде матрицы: колонка для нового `deprecated`-поля не рендерится на записях с
   `registry_version ≥ deprecated_since`; на старых записях поле видно и read-only (§6.1).
